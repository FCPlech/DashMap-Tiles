# DashMap-Tiles

<p align="center">
  <img src="branding/dashmap_logo.png" alt="DashMap logo" width="400" />

Offline map releases for DashMap: ready-made routing tiles and street
databases, one GitHub Release per region. This repo is only the hosted
releases; it builds nothing and references no build tooling.

This repo stores **no map data in git**. Git only tracks metadata, scripts and
docs. The actual multi-GB files live as **GitHub Release assets**, one release
per region.

## How it fits together

This repo hosts versioned, ready-made map releases. The DashMap app fetches
a region's zips straight from the GitHub Releases hosted here, with no desktop
needed. Riders who want fresher data than the latest release can prepare
their own routing/street files with their own tooling and sideload them;
that path never touches this repo.

## Release convention

- **One release per region.** Tag format: `<CC>-<slug>-vYYYY.MM.DD`
  (e.g. `BR-brazil-v2026.09.16`, `BR-sul-v2026.09.16`), with the ISO country
  code up front.
  The slug is a short region id (e.g. the Geofabrik extract id the files
  were built from), lower-case, filesystem-safe. The display name carries an
  ISO country prefix (e.g. BR-Sul, BR-Brazil) so regions from different
  countries stay identifiable.
- Each release carries **both datasets** (when available):
  - Offline Routing (Valhalla tiles)
  - Nearby Streets (SQLite)
- Each release also carries a `release-manifest.json` and `SHA256SUMS`
  (see "File layout" below).

## File layout per release

Every dataset ships as **one zip** (transport packaging only). Inside each
zip are the **exact on-device filenames**, so the app (or a manual `unzip`)
extracts straight into the target dir with no renaming:

| Asset (zip) | Zip contents → installed on device at |
|---|---|
| `valhalla.zip` (or split parts, see below) | `valhalla_tiles.tar` → `…/files/valhalla/valhalla_tiles.tar` |
| | `manifest.json` (from `--valhalla-manifest`) → `…/files/valhalla/manifest.json` |
| | `valhalla.json` → `…/files/valhalla/valhalla.json` |
| | `admin.sqlite` → `…/files/valhalla/admin.sqlite` (when built) |
| | `timezones.sqlite` → `…/files/valhalla/timezones.sqlite` (when built) |
| `streets.zip` | `streets-brazil.sqlite` (from `--streets-db`, stored under this fixed name, which is the filename the app reads whatever the input file was called) → `…/files/offline_streets/streets-brazil.sqlite` |
| | `manifest.json` (from `--streets-manifest`) → `…/files/offline_streets/manifest.json` |
| `release-manifest.json` | generated by `scripts/publish_region.py`: describes the release (not zipped, the app fetches it first to know what to download) |
| `SHA256SUMS` | generated by `scripts/publish_region.py` (not zipped) |

These are the fixed on-device locations the app reads, so a downloaded
release and self-prepared files are interchangeable on the phone.

### Zips over 2 GB

GitHub rejects any single Release asset over 2 GB. A full-country
`valhalla.zip` can exceed that. In that case the publish script splits
it into ~1.5 GB chunks:

```
valhalla.zip.part-aa
valhalla.zip.part-ab
…
```

The app (or manually: `cat valhalla.zip.part-* > valhalla.zip`, then
`unzip`) reassembles them in lexicographic order. `release-manifest.json`
records per dataset whether it is `single` or `split`, the zip's member
list (`contents`), plus per-file hashes. Never publish a truncated zip.
`verify_release.py` checks all of this before upload (`--deep` also
reassembles splits and CRC-checks every member).

## Discovery: `tiles-index.json`

`tiles-index.json` at the repo root is the **only tracked file the app
needs at runtime**. It lists every region and its latest release:

```json
{
  "schema": 1,
  "indexUrl": "https://raw.githubusercontent.com/FCPlech/DashMap-Tiles/main/tiles-index.json",
  "regions": [
    {
      "slug": "brazil",
      "displayName": "BR-Brazil",
      "latest": "BR-brazil-v2026.09.16",
      "releaseUrl": "https://github.com/FCPlech/DashMap-Tiles/releases/tag/BR-brazil-v2026.09.16",
      "manifestUrl": "https://github.com/FCPlech/DashMap-Tiles/releases/download/BR-brazil-v2026.09.16/release-manifest.json"
    }
  ]
}
```

The app flow (future): fetch `tiles-index.json` → pick region → fetch that
release's `release-manifest.json` → download each zip (reassembling `.part-*`
when split) → verify SHA-256 → unzip straight into the install dirs above.
`scripts/build_index.py` regenerates the index entry after each publish; see
`docs/RELEASE-PROCESS.md`.

## Where the data comes from

This repo does **not** build map data: nothing here creates routing tiles
or street databases, and the scripts here never will. They only take
already-prepared files and **pack them** (`publish_region.py` → zips +
manifest), **validate them** (`verify_release.py`) and **index them**
(`build_index.py`). Prepare the input files with whatever tooling you use
(the expected files per dataset are listed in `docs/RELEASE-PROCESS.md`),
then pack them here.
