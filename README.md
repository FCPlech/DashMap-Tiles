# DashMap-Tiles

Pre-built offline map releases for [DashMap](https://github.com/FCPlech/DashMap)
(the low-power motorcycle navigation app for the Royal Enfield Himalayan 450 /
Tripper dash).

This repo stores **no map data in git**. Git only tracks metadata, scripts and
docs. The actual multi-GB files live as **GitHub Release assets**, one release
per region.

## How it fits together

There are two ways a rider gets offline maps onto the phone:

1. **Download ready-made (this repo, future app feature)** — the DashMap app
   fetches a region's files straight from the GitHub Releases hosted here.
   No Docker, no osmium, no desktop needed.
2. **Build your own fresher copy (DashMap repo)** — `tools/update_offline_data.py`
   in the main DashMap repo downloads the OSM extract and builds routing +
   streets locally with Docker/osmium, then sends them over USB/Wi-Fi.
   That path never touches this repo.

The desktop tool gains **no new feature** from this repo. The future consumer
is the **DashMap Android app** itself.

## Release convention

- **One release per region.** Tag format: `<slug>-vYYYY.MM.DD`
  (e.g. `brazil-v2026.09.16`, `sao-paulo-v2026.09.16`).
  The slug is the Geofabrik region id (`region_catalog.py` in the DashMap
  repo), lower-case, filesystem-safe — the same folder name used under
  `tools/map_build/regions/<slug>/`.
- Each release carries **both datasets** (when available):
  - Offline Routing (Valhalla tiles)
  - Nearby Streets (SQLite)
- Each release also carries a `release-manifest.json` and `SHA256SUMS`
  (see "File layout" below).

## File layout per release

Every dataset ships as **one zip** (transport packaging only). Inside each
zip are the **exact on-device filenames**, so the app — or a manual `unzip` —
extracts straight into the target dir with no renaming:

| Asset (zip) | Zip contents → installed on device at |
|---|---|
| `valhalla.zip` (or split parts, see below) | `valhalla_tiles.tar` → `…/files/valhalla/valhalla_tiles.tar` |
| | `manifest.json` (from the build's `valhalla/manifest.json`) → `…/files/valhalla/manifest.json` |
| | `valhalla.json` → `…/files/valhalla/valhalla.json` |
| | `admin.sqlite` → `…/files/valhalla/admin.sqlite` (when built) |
| | `timezones.sqlite` → `…/files/valhalla/timezones.sqlite` (when built) |
| `streets.zip` | `streets-brazil.sqlite` (from the build's `streets/streets-brazil.sqlite` — note: the builder's filename is fixed even for non-Brazil regions, and that legacy name is what the app already reads, so it is kept as-is) → `…/files/offline_streets/streets-brazil.sqlite` |
| | `manifest.json` (from the build's `streets/streets-manifest.json`) → `…/files/offline_streets/manifest.json` |
| `release-manifest.json` | generated by `scripts/publish_region.py` — describes the release (not zipped: the app fetches it first to know what to download) |
| `SHA256SUMS` | generated by `scripts/publish_region.py` (not zipped) |

Device paths mirror what `update_offline_data.py` (`DATASETS`) and
`push_offline_data.sh` already use, so a downloaded release and a
locally-built region are interchangeable on the phone.

### Zips over 2 GB

GitHub rejects any single Release asset over 2 GB. A full-country
`valhalla.zip` can exceed that. In that case the publish script splits
it into ~1.5 GB chunks:

```
valhalla.zip.part-aa
valhalla.zip.part-ab
…
```

The app (or manually: `cat valhalla.zip.part-* > valhalla.zip`, then
`unzip`) reassembles them in lexicographic order. `release-manifest.json`
records per dataset whether it is `single` or `split`, the zip's member
list (`contents`), plus per-file hashes. Never publish a truncated zip —
`verify_release.py` checks all of this before upload (`--deep` also
reassembles splits and CRC-checks every member).

## Discovery: `tiles-index.json`

`tiles-index.json` at the repo root is the **only tracked file the app
needs at runtime**. It lists every region and its latest release:

```json
{
  "schema": 1,
  "indexUrl": "https://raw.githubusercontent.com/<org>/DashMap-Tiles/main/tiles-index.json",
  "regions": [
    {
      "slug": "brazil",
      "displayName": "Brazil",
      "latest": "brazil-v2026.09.16",
      "releaseUrl": "https://github.com/<org>/DashMap-Tiles/releases/tag/brazil-v2026.09.16",
      "manifestUrl": "https://github.com/<org>/DashMap-Tiles/releases/download/brazil-v2026.09.16/release-manifest.json"
    }
  ]
}
```

The app flow (future): fetch `tiles-index.json` → pick region → fetch that
release's `release-manifest.json` → download each zip (reassembling `.part-*`
when split) → verify SHA-256 → unzip straight into the install dirs above.
`scripts/build_index.py` regenerates the index entry after each publish; see
`docs/RELEASE-PROCESS.md`.

## Building maps locally

This repo does **not** build tiles — nothing here creates map data, and the
scripts here never will. The full build pipeline (OSM extract download,
Valhalla tiles via Docker, streets database via osmium) lives in the main
DashMap repo:

```bash
git clone https://github.com/FCPlech/RoyalMap.git
cd DashMap
./tools/update_offline_data.py   # Download Maps → builds into tools/map_build/regions/<slug>/
```

The scripts in *this* repo only take that already-built folder and
**package it** (`publish_region.py` → zips + manifest), **validate it**
(`verify_release.py`) and **index it** (`build_index.py`) — see
`docs/RELEASE-PROCESS.md`.
